# JZ02V10 (THWC 4G LTE stick)

This page records the OpenWrt profile and the open questions for the
**JZ02V10**, an MSM8916 4G stick from THWC (Zhihe). It is **not** the same
board as the [JZ02](JZ02.md) battery MiFi: the two share the SIM GPIO *set*
(1 / 20 / 22 / 23) but drive it with different semantics, and the JZ02V10 has
no battery in the reference firmware.

The port follows the `openstick-jz02v10` device of the immortalwrt tree
(`dts/msm8916-thwc-jz02v10.dts`), which is what the
[immortalwrt-Actions-410](https://github.com/jiangmo/410-immortalwrt-Actios)
build repo ships as `jz02v10`.

## Build identity

- Build alias: `jz02v10`
- OpenWrt device profile: `thwc-jz02v10`
- DTS: `msm8916-thwc-jz02v10` (patch 869), based on `msm8916-ufi.dtsi`
- `SUPPORTED_DEVICES`: `jz02v10,generic thwc,jz02v10`
- `board_name` at runtime: `jz02v10,generic`
- Recovery partition: **yes** (`GPT_RECOVERY := 1`, 17-partition layout)
- Ramoops: yes (`ramoops@8db00000`, 1 MiB)

The second `SUPPORTED_DEVICES` entry is the upstream identity
(`thwc,jz02v10`). It exists so `sysupgrade` keeps working on a unit that still
runs the reference openstick image, whose `board_name` is that string.

## Hardware

| | |
| :-- | :-- |
| SoC | MSM8916 |
| RAM | ~390 MB visible (shared MSM8916 baseline) |
| eMMC | **not measured** — see below |
| Form factor | bus-powered stick, no battery in the reference firmware |
| Stock OS | Android (vendor image) |

`GPT_TOT_SECTORS` is left at the target default (4 GB / 7,569,408 sectors) on
purpose: the eMMC size has not been read off a unit yet. The default is the
safe side — `flash.sh` reads the real size at flash time, and a too-small
value only leaves unused space at the end of the disk, while a too-large one
would put the backup GPT header past the end of the device.

To fix it once a unit is in hand:

```sh
cat /sys/block/mmcblk0/size          # or: edl printgpt | grep sectors
```

then set `GPT_TOT_SECTORS` in the `Device/thwc-jz02v10` block.

## LEDs

The tri-colour nodes come from `msm8916-ufi.dtsi`; this board wires them to the
reference GPIOs and keeps the inherited function/colour pairing, which is what
the LED monitors resolve:

| Lamp | GPIO | DTS name | Used by |
| :--- | ---: | :------- | :------ |
| red | 8 | `red:power` | power-off blink (`rc.button/power`), `wan_fault` fallback |
| green | 6 | `green:wlan` | `wifi-led-monitor` |
| blue | 7 | `blue:wan` | `modem-led-monitor` (see `leds.sh`) |

`leds.sh` has a `*jz02v10*` branch for the `wan` role, because the board has a
blue cellular lamp and no green WAN lamp; without it the cellular role would
resolve to a label that does not exist and stay dark.

## SIM

Four one-hot switch lines, exposed as `gpio-leds` so userspace can drive them
through `/sys/class/leds` — the same interface the reference firmware uses:

| Label | GPIO | Slot |
| :---- | ---: | ---: |
| `sim:sel` | 1 | 1 |
| `sim:en` | 20 | 2 |
| `sim:sel2` | 22 | 3 |
| `sim:en2` | 23 | 4 |

`sim-select-jz02v10` (START=20) reads `sim.slot` from UCI (default **1**),
drops every line and raises exactly one. Unlike the JZ02 there is **no
hot-detect pulse**: the reference firmware does not pulse anything on this
board, it only holds one line.

```sh
uci set sim.slot=3 && uci commit sim
/etc/init.d/sim-select-jz02v10 restart
/etc/init.d/sim-select-jz02v10 status     # slot N selected (sim:...)
```

The JZ02 keeps its own `/etc/init.d/sim-select` (three lines plus pulse,
default slot 3) and `sim-test`; both scripts exit immediately on the other
board, so the two can ship side by side.

## Reset / failsafe

The reference device tree puts the Restart key on **GPIO37**, active high with
a pull-down — the same pin the stock Android DTB calls `key_f2`. Failsafe mode
is therefore expected to work the standard way: **tap once inside the 7 s
preinit window** and reach `192.168.10.1` over the USB gadget. This has not
been confirmed on hardware yet; if the pinhole turns out to be a hardware
reset (as on the JZ02), disable `button_restart` in the DTS the way patch 868
does.

## Deliberately not set

- **Battery / charger.** The reference image is bus-powered, so the
  `msm8916-ufi.dtsi` `pm8916_usbin` extcon is kept and no `battery` /
  `pm8916_charger` / `pm8916_bms` block is added, and `luci-app-battery` is
  **not** in `DEVICE_PACKAGES`. If a unit turns out to have a cell, copy the
  battery block from patch 868 (JZ02, 2100 mAh / 4.35 V) and add the package.
- **`qcom,a2-pin` on `&bam_dmux`.** The reference device does not need it. If
  this unit's modem starts logging `modem pc-ack timeout during resume` under
  data traffic, add the property (patch 868 documents the failure mode).
- **SIM hot-swap.** Untested; the `sim-hotplug` service is present but no
  `sim_hotplug` line has been confirmed on this board.

## Validated on hardware

Nothing yet. This profile is a **build-only port** of the reference device:
the GPIO map is taken from the reference DTS, not from a unit on a bench.

## Feedback we need

If you have a JZ02V10, please report:

1. `cat /sys/block/mmcblk0/size` — the real eMMC size, so `GPT_TOT_SECTORS`
   can be set correctly.
2. Whether the Restart pinhole produces `KEY_RESTART` (failsafe works) or is a
   hardware reset.
3. Whether the unit has a battery, and if so its label (mAh / charge voltage).
4. Which SIM slots are populated, and whether `sim.slot` 1–4 select them
   correctly.
5. Any `a2_power` / `pc-ack timeout` events after hours of data traffic.

Open an issue with `dmesg`, `logread` and `mmcli -m 0`.
